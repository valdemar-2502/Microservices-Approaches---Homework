### Выбор: **GitLab**

**Почему GitLab:**

1. **Один продукт закрывает всё.** Хранение кода (Git), CI/CD и реестр образов находятся в одной системе. Не нужно настраивать связки между разными сервисами.
2. **Облачная система.** gitlab работает как сервис, обслуживать сервер самим не нужно. При этом тяжёлые сборки можно отдать на собственные серверы через GitLab Runner.
3. **Подходит под схему.** Репозиторий на сервис, свой артефакт (Docker-образ с версией) на сервис, стадии «сборка → тесты → выкладка», разные стенды.
4. **Все требования выполняются стандартными средствами.** Запуск по push и по кнопке с переменными, шаблоны через `include`, секреты через защищённые переменные, параллельные тесты через `parallel`.

**Минус:** по возможностям GitHub Actions очень близок. GitLab выбран из-за встроенного реестра и удобной работы с пайплайнами из одного файла, но GitHub тоже был бы допустимым выбором.

**Принципы работы:**

1. Разработчик делает commit в репозиторий своего сервиса. Событие автоматически запускает пайплайн этого сервиса.
2. Пайплайн выполняется на раннерах (GitLab Runner), развёрнутых на собственных серверах. Сборка идёт в **собственном Docker-образе** с нужными инструментами.
3. Тесты идут от быстрых к медленным (пирамида): сначала unit-тесты, затем сервисные, потом end-to-end. Если ранний этап упал, дальше пайплайн не идёт. Тесты внутри одной стадии запускаются параллельно.
4. Готовый артефакт (Docker-образ с версией, например `orders:1.2.3`) попадает в Container Registry.
5. Образ автоматически выкладывается на стенды Dev, Integration и UAT. В Production выкладка запускается **вручную кнопкой** (непрерывная поставка), стратегия Rolling или Blue-Green, чтобы не было простоя.
6. Секреты (пароли, ключи) хранятся в защищённых переменных GitLab, в логах они скрыты.
7. Если нужно запустить сборку с особыми настройками, используется кнопка **Run pipeline** с указанием переменных.

### Пример `.gitlab-ci.yml`

```yaml
include:
  - project: company/ci-templates      # общий шаблон для всех сервисов
    file: /docker-build.yml

stages: [build, test, deploy]

build:
  stage: build
  image: registry.gitlab.com/company/ci-images/builder:1.0   # собственный образ
  script:
    - make build
  tags: [docker-runner]                # запуск на собственном раннере

unit-tests:
  stage: test
  parallel: 4                          # тесты идут параллельно в 4 заданиях
  script:
    - make test SHARD=$CI_NODE_INDEX TOTAL=$CI_NODE_TOTAL

deploy-prod:
  stage: deploy
  when: manual                         # выкладка в Production по кнопке
  script:
    - ./deploy.sh $IMAGE_VERSION
```

Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;

## Ответ:
Сбор логов со всех хостов в центральное хранилище; минимальные требования к приложениям (сбор из stdout); гарантированная доставка; поиск и фильтрация; интерфейс с доступом для разработчиков; ссылка на сохранённый поиск.

### Выбор: **ELK-стек (Filebeat → Logstash → Elasticsearch → Kibana)**

**Почему ELK:**

1. **Приложениям ничего не нужно делать.** Они пишут в stdout, как требуют «12 факторов» (логи как поток событий). Docker сохраняет вывод контейнера в файл на хосте, а агент его читает.
2. **Надёжная доставка.** Агент Filebeat запоминает, до какого места прочитан файл, и после сбоя продолжает с того же места. Logstash может хранить очередь на диске. В итоге логи доходят хотя бы один раз, то есть не теряются.
3. **Мощный поиск.** Elasticsearch индексирует текст, поэтому можно искать по любому слову и фильтровать по сервису, хосту, уровню, времени.
4. **Удобный интерфейс для разработчиков.** В Kibana разработчикам выдаются роли только на чтение и доступ к нужным индексам, а найденный поиск можно сохранить (Saved search) и отправить коллеге ссылкой.

**Минус:** ELK требует заметных ресурсов. Если нагрузка небольшая и важна лёгкость, подошёл бы Loki с Grafana.

**Принципы работы:**

1. Сервисы пишут логи в **stdout**, и больше ничего от них не требуется.
2. На **каждом хосте** запущен агент (Filebeat), он читает файлы логов контейнеров и добавляет метки: имя хоста, сервиса, контейнера.
3. Логи передаются в **Logstash**, который разбирает записи (например, JSON), обогащает их и держит очередь на диске на случай недоступности хранилища.
4. Logstash записывает данные в **Elasticsearch**, он хранит логи и позволяет быстро искать.
5. Разработчики заходят в **Kibana** (через единый вход SSO), ищут по записям, фильтруют, сохраняют поиск и делятся ссылкой на него.

## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.

## Ответ:
Метрики со всех хостов; метрики ресурсов хостов (CPU, RAM, HDD, Network); те же метрики для каждого сервиса; метрики, специфичные для сервиса; интерфейс с запросами и агрегацией; интерфейс с настраиваемыми панелями.

| Требование | **Prometheus + Grafana** | InfluxDB + Telegraf + Grafana | Zabbix | Datadog |
|---|---|---|---|---|
| Сбор метрик со всех хостов | Да node_exporter на каждом хосте | Да Telegraf на каждом хосте | Да Zabbix agent | Да агент |
| CPU, RAM, HDD, Network хоста | Да node_exporter | Да Telegraf | Да | Да |
| Те же метрики по каждому сервису | Да cAdvisor (по контейнерам) | Да Telegraf (Docker input) | Частично шаблоны для Docker, настройка сложнее | Да |
| Метрики самого сервиса | Да сервис отдаёт `/metrics` | Частично через Telegraf или запись в базу | Частично нужно вручную описывать элементы данных | Да |
| Запросы и агрегация | Да язык PromQL | Да InfluxQL, Flux | Частично ограниченные запросы | Да |

| Бесплатно | Да | Да | Да | Нет платный SaaS |

### Выбор: **Prometheus + Grafana** (с node_exporter и cAdvisor)

**Почему именно это:**

Каждый сервис публикует метрики по адресу `http://host/metrics`, Prometheus регулярно считывает их и сохраняет, Grafana показывает графики. Для сервисов это минимальное требование: подключить библиотеку метрик и открыть один адрес.
1. **Все метрики покрыты:**
   - ресурсы хостов (CPU, RAM, диск, сеть) даёт **node_exporter**;
   - ресурсы каждого сервиса (контейнера) даёт **cAdvisor**;
   - метрики самого сервиса (число заказов, время ответа, ошибки) сервис отдаёт сам на `/metrics`.
2. **Запросы и агрегация.** Язык PromQL позволяет суммировать, усреднять, считать процентили и группировать метрики по сервису или хосту.
3. **Панели.** В Grafana можно собрать собственные дашборды для разных команд, а доступ выдать по ролям.
4. **Бесплатно** Хорошо работает с контейнерами и Kubernetes, есть готовые дашборды.

**Минус:** Prometheus по умолчанию хранит данные на одном сервере. Для долгого хранения и большого масштаба понадобится дополнительное решение (например, Thanos или VictoriaMetrics).

**Принципы работы:**

1. Prometheus сам **обходит** (pull) все цели по расписанию, например раз в 15 секунд, и сохраняет значения метрик.
2. Цели автоматически находятся через конфигурацию или автообнаружение (Docker, Kubernetes).
3. В Grafana подключается Prometheus как источник данных. Команды строят графики запросами PromQL и собирают панели.
4. На основе метрик в Prometheus описываются правила оповещений, а Alertmanager отправляет их в почту или мессенджер.

### Трассировка

Мониторинг состоит из трёх частей: метрики, логи и трассировка. Первые две закрыты решениями выше. Для трассировки (путь запроса через несколько сервисов) можно добавить **Jaeger**: на каждом хосте работает Jaeger Agent, данные собирает Jaeger Collector, хранит база (Cassandra или Elasticsearch), смотреть удобно в Jaeger UI.
